# 多对话协作约定

本文件面向用户将来手动建立的多个项目对话。本次没有自动创建对话，也不要求自动派生代理。

## 开始一个任务

1. 读入口、需求、进度，执行 `git status --short`、`git branch --show-current` 和 `git log -5 --oneline`。
2. 先在用户协调下明确本对话目标、负责文件和依赖。不要把多个互相依赖的大改动分给并行对话而不设集成人。
3. **有并行代码任务时使用独立 Git 工作树与分支**，不要让多个对话同时写 `E:\GPT\EVCam` 同一个目录。示例：

```powershell
git -C E:\GPT\EVCam worktree add -b task/ui-next E:\GPT\EVCam-worktrees\ui-next e5-ui-layout-test-11140102
```

每个任务使用不同目录/分支名，在该工作树打开对应开发对话。此命令是后续示例，本次未建立额外工作树。串行任务可以继续主目录，但必须确认没有另一个对话写入。

## 协调记录

`work/ACTIVE_TASKS.md` 是同机共享任务登记表，不纳入 Git，只有指定协调对话写入。初次迁移时没有登记任何并行任务。任务对话在自己的工作树 `docs/tasks/<task-id>.md` 记录进度，避免并行修改同一份 `docs/STATUS.md`。

登记字段：任务 ID、对话职责、工作树、分支、负责文件、依赖、状态、最新提交、是否已集成。开始前读登记表；记录失效或有冲突时先协调，再修改受影响文件。

独立工作树的 `work/`/`outputs/` 不自动共享；构建脚本通过 `-SharedRoot` 访问主项目工具。不要为省事把两个工作树的 `app/build` 指向同一个目录。

## 完成与集成

- 每个任务交付：改了什么、准确提交、验证结果、未验证风险、后续要求。未做的实测明确写出。
- 指定一个集成对话审查/合并提交，解决冲突，统一更新 `docs/STATUS.md` 与需求/架构，并重新完成与合并范围相称的检查。
- 发布由集成对话统一进行，避免多对话生成相同版本名、标签或覆盖 APK。
- 不擅自 reset/clean、覆盖其他对话的未提交修改、强推分支或批量格式化他人负责文件。
- 不假设其他对话已读本对话聊天记录。新的重要决定必须落到文件，再由协调人通知相关任务。

## 推荐拆分

可按录像资源/性能、UI、飞书/HUD 实测、集成发布拆分职责；这只是组织建议，不是立即执行的任务。涉及相同生命周期或配置文件的改动先串行或安排统一集成。
