包名 `com.yuan.smartcam`，versionName `3.0.40`。SHA-256：`352ce9a0902fbe88038709b83195c4cce6a099847cea5d57d07a2a0a2fc195a5`。

使用本机 Androguard 解析 DEX、对关键方法反编译，并保留指令进行交叉核对。类名已混淆，自动反编译存在类型/控制流还原瑕疵，以下只总结可由调用和指令确认的主录像路径，不声称覆盖所有功能或运行时分支。

| 方面 | Smartcam 已确认实现 | EVCam 当前实现与含义 |
| --- | --- | --- |
| 主录像形态 | `oy2.f()` 遍历布局内多摄像头纹理绘制合成图；`jy2` 主录像启动创建一个 `ey1` 并连接 `Encoder` 输出 | 日常三路各建一个 `CodecVideoRecorder`，分别输出 MP4。合成单视频与三路独立文件的编码负载、清晰度分配不同 |
| 摄像头输出 | `vz` 为每摄像头配置单个 Surface，RECORD 模板不支持时回退 PREVIEW | `SingleCamera` 录像与预览可能使用独立硬件流；主预览/HUD/补盲按需求管理。是否成为瓶颈需车机测量 |
| 源帧率 | `vz.a()` 查询支持范围，优先匹配目标 25 fps，设置 AE FPS range，失败回退 HAL 默认 | 当前 `SingleCamera` 没有设置 `CONTROL_AE_TARGET_FPS_RANGE`。只给编码器配置 25 fps 不保证摄像头实际供给 25 fps |
| 编码器选择 | `lp2.e/c/b()` 检查硬件、Surface 格式、尺寸对齐、尺寸+帧率支持、可达到帧率与可用性能点；尝试配置，不合适时尝试候选分辨率 | `CodecVideoRecorder` 主要按 MIME/名称选编码器；HEVC 优先。需要补足具体尺寸/帧率和多实例实际能力证据 |
| 编码格式 | 主录像配置 `video/avc`；设置码率、帧率、1 秒关键帧间隔，条件支持时设置 VBR/实时优先级/operating-rate，并有配置回退 | 当前样本 HEVC；EVCam 已有强制 H.264 选项。H.264 值得同条件对照，但不能承诺其必然更快或更省电 |
| 线程 | `recorder-gl`、独立输出线程、`codec-drain`、`recorder-writer`、quota/monitor 等分工 | EVCam 取帧、GL 提交、drain 和 `MediaMuxer.writeSampleData()` 在同一 encoder Handler 执行。写盘或封装阻塞可能反向拖慢取帧 |
| 待写队列 | 编码数据复制到可复用缓冲后交给 writer，及时释放 codec 输出缓冲；`uq` 限制最多 32 MiB / 1024 个待写项 | 当前没有独立的有界编码数据写盘队列。异步拆分必须配套容量、所有权和停止/分段收尾设计，不能无限堆内存 |
| 积压恢复 | 低水位条件约 16 MiB / 512 项，积压时会舍弃数据并等待关键帧恢复，日志明确提示录像缺口 | 不能将“线程不被卡住”解释成“没有漏录”；行车录像应明确记录缺口并尽量避免触发 |
| GL 缓冲 | `oy2.c()` 创建 6 个 RGBA atlas 纹理/FBO，按引用/可用槽调度，多个输出复用合成结果 | 这是额外 GPU 缓冲开销，不能因单编码器就断言总内存更低；EVCam 三路独立录制不应直接搬入整套合成架构 |
| 性能证据 | 日志覆盖源帧间隔、GL、swap、drain、writer、队列积压、线程 CPU 等 | EVCam 已有部分段末帧率统计，但不足以从本段 MP4 锁定是哪一环造成间隔 |

本地审计证据在 `work/smartcam-analysis/`：`recording-api-index.txt`、混淆类 `.txt` 指令与 `.java` 反编译摘录。脚本 `work/inspect_smartcam.py`、`work/decompile_smartcam.py`、`work/decompile_smartcam_more.py`。反编译产物只保留在忽略目录，没有复制进应用或纳入 Git。

## 建议的下一轮工作

1. 先增加低频聚合统计：摄像头源时间戳/回调、实际 latch 次数、主动跳帧、GL 与 swap 耗时、codec 输出、写盘耗时和最大延迟、编码器名称、实际输出数量；覆盖停止与分段，避免逐帧刷日志。
2. 优先评估把写盘与取帧/GL 拆开，并配置小而有界的编码数据缓冲、背压与可追踪的缺口行为。它比继续修改 UI 更直接针对当前管线中的阻塞耦合，但本次没有证据证明内置存储就是主因。
3. 补充摄像头支持的 FPS range 和编码器能力检测；只选择设备支持的配置。夜间固定较高帧率可能改变曝光/亮度，需要画质对照；不把设置值当成实际帧率。
4. 可用当前版本先做短对照：同一场景、内置存储、日常三路、HUD 条件相同，仅切换实时预览开/关；再固定其他条件对比 HEVC/强制 H.264。这样能区分预览输出压力与编码格式影响，避免一次改多个因素。
5. 保留日常三路独立录像、飞书四路及交接、转向补盲、HUD 副屏/EVCC 和 Wi-Fi/ESP32；不直接改成 Smartcam 的合成单文件方式。若实施代码优化，再按规范更新版本、验证并提供测试 APK。

结论边界：本片确认存在低且不均匀的实际帧更新；最新 UI 版没有新的录像核心修复；Smartcam 在调度隔离、能力检查和性能统计方面有可借鉴的设计，但没有它在 E5 上的实测视频和负载数据，不能判定它一定更流畅，也不能仅凭当前文件锁定 CPU、GPU、存储或摄像头 HAL。

## 补充：刹车等车辆状态水印的开销

用户追问该功能是否影响性能。本次继续静态检查，未实施新功能。

- `il.a()` 在 Encoder/Live 输出路径绘制画面之后、提交编码 Surface 之前调用 `nb4.a(width,height)`，复用现有 GL/编码路径。
- `nb4.a()` 比较当前秒数和 `o03.b` 状态快照：两者未变时跳过文字/纹理更新；跨秒或状态改变时重新生成显示内容。不能把它描述为严格每秒只更新一次，车速等快变状态仍可能频繁触发更新。
- 复用一个 1024×132 ARGB_8888 Bitmap、Canvas、Paint 和 GL 纹理；首次上传 `texImage2D`，后续 `texSubImage2D`，通过 GL 绘制叠加。该 Bitmap 像素约 528 KiB，仅为局部资源，不代表功能或进程总内存。
- VHAL 路径可见属性流订阅和兴趣属性过滤调用；信号接收、解析、快照更新本身也有开销，实际取决于启用的数据源、订阅规模和更新频率。
- 因而该功能不是零成本；缓存小区域并复用编码管线通常比重新处理整幅视频轻，但没有在 E5 上测量，不能提供 CPU/fps 百分比或断言没有影响。频繁状态更新、较大绘制面积和多路独立重复叠加会增加负担。
- 若以后在本项目增加，应按需启用、复用已有车辆信号订阅、缓存图标/文字，只在必要时更新纹理，并保留刹车等边沿状态的及时性；先测开/关对照，不用固定低频刷新掩盖短促事件。
